# 업데이트·업데이트 역량 개발 (WI-VCSMS-02-09-01)

> 상위 절차: [[PRO-VCSMS-02-09_운영_업데이트_및_지원종료_폐기_절차]] · 기준: [[표준프로세스_구성원칙]]

## 1. 업무 목적
운영 단계에서 차량 내 소프트웨어 업데이트(및 그 업데이트를 적용하는 역량)를 ISO/SAE 21434 준거로 개발한다. 사고 대응·취약점 조치 등으로 업데이트가 필요할 때, 본 표준의 개발 V-model 을 재적용하여 업데이트 자체가 새로운 사이버보안 위험을 도입하지 않도록 한다. (VCSMS-R-099 / [RQ-13-03])

> 본 WI 는 선택(mandatory: false) — 차량 내 업데이트 역량을 보유·운영하는 경우에만 적용.

## 2. 수행 주체
- **주 수행자**: 개발팀
- **검토자**: 운영/필드
- **승인자**: Cybersecurity Manager (CSM)

## 3. 범위
PRO-VCSMS-02-09 §5 단계 1(업데이트 개발)에 적용한다. 업데이트 개발의 상세 엔지니어링 활동은 [[PRO-VCSMS-02-05_제품개발_사이버보안_엔지니어링_절차]] V-model 을 재적용한다. 차량 내 업데이트 인프라(SUMS) 일반은 UNECE R156([[REF-002_UNECE_R156_SUMS_요약_v0.1]], 인터페이스 대상)과 정합한다.

## 4. 입력 자료 / 산출물
- **Input**
  - 업데이트 트리거(취약점 조치·사고 대응([[PRO-VCSMS-01-04_사이버보안_사고_대응_절차]])·기능 변경)
  - 영향받는 item/component 의 사이버보안 케이스·요구
  - SUMS(R156) 업데이트 적용 제약·롤백 요건
- **Output**
  - [[TMP-VCSMS-02-09-01-01_업데이트_개발_명세서]] 작성분
  - 개발 V-model 재적용 산출물(요구·설계·검증) 참조

## 5. 수행 절차 (단계별)

### 5.1 사전 준비
1. 업데이트 트리거를 분류한다(보안 패치·사고 대응·기능/규제 변경)하고 긴급도를 판정한다.
2. 영향 범위(대상 item/component·차종·VIN 범위)를 식별한다.
3. 기존 사이버보안 케이스·요구를 확보하여 업데이트의 영향 평가 기준선으로 삼는다.

### 5.2 수행 단계
1. **업데이트 요구 정의**
   - 업데이트가 충족할 사이버보안 요구(패치 대상 취약점·새 기능 위험)를 정의한다. (VCSMS-R-099 / [RQ-13-03])
2. **영향 평가(델타 TARA)**
   - 업데이트가 기존 위협·자산에 미치는 영향을 평가한다(필요 시 TARA([[PRO-VCSMS-02-03_위협분석_및_리스크평가_TARA_절차]]) 델타 수행).
3. **개발 V-model 재적용**
   - PRO-VCSMS-02-05 의 설계·구현·통합 활동을 업데이트 범위에 맞게 재적용한다.
4. **업데이트 역량 요건 반영**
   - 무결성·인증된 배포, 롤백, 실패 안전(safe-state) 등 업데이트 적용 역량 요건을 반영한다(R156 정합).
5. **CSM 검토·승인**
   - CSM 이 업데이트 요구·영향 평가·역량 요건 충족을 검토·승인하고, 검증 단계(WI-09-02)로 인계한다.

### 5.3 완료 조건
- [ ] 업데이트 트리거·긴급도가 분류되었다
- [ ] 영향 범위(item/차종/VIN)가 식별되었다
- [ ] 업데이트 사이버보안 요구가 정의되었다
- [ ] 델타 영향 평가(필요 시 TARA)가 수행되었다
- [ ] 개발 V-model 재적용 및 업데이트 역량 요건(무결성·롤백) 반영이 완료되었다
- [ ] CSM 검토·승인이 완료되었다

## 6. 인터페이스 부서
- **운영/필드**: 배포 제약·차량 상태 정보 제공
- **SUMS 운영(R156)**: 업데이트 인프라·롤백 정합
- **CSM 조직**: 영향 평가·요구 충족 검토

## 7. 주의사항 / 예외 처리

### 7.1 긴급 보안 패치(사고 대응 연계)
- 사고 대응([[PRO-VCSMS-01-04_사이버보안_사고_대응_절차]])에서 긴급 패치가 요구되면, 정식 V-model 전체 대신 위험 비례 축약 절차(핵심 요구·영향 평가·검증 우선)를 적용하되, 사후 정식 산출물을 보완한다. CSM 이 축약 범위를 승인한다.

### 7.2 업데이트가 새 위험 도입
- 영향 평가 결과 업데이트가 허용 불가 새 위험을 도입하면, 배포하지 않고 설계를 재검토한다. 위험 수용이 불가피하면 보상 통제와 함께 CSM·Project CS Lead 의 수용 결정을 기록한다.

### 7.3 롤백 불가 업데이트
- 기술적으로 롤백이 불가능한 업데이트는, 실패 시 차량을 안전 상태로 유지하는 대체 안전장치(safe-state·재시도)를 반드시 정의한 뒤에만 진행한다.
