# 보안 요구사항 정의 및 검토 (WI-MDCS-01-02-02)

> 상위 절차: [[PRO-MDCS-01-02_보안_SW_개발_프로세스_절차_v0.1]] · 상위 방침: [[POL-MDCS-01_헬스SW_제품_보안_거버넌스_방침_v0.1]]

## 1. 업무 목적
헬스SW 의 설치·운영·유지·폐기 전 수명주기에 걸친 보안 능력 요구를 도출·문서화하고, 시험 가능성·무모순성 등 품질 기준으로 검토하며, REQUIRED SW(사용자 환경 제공 SW)와 관련된 리스크를 식별하여, 설계·구현·검증의 추적 기반을 마련한다. (5.2.1, 5.2.2, 5.2.3)

## 2. 수행 주체
- **주 수행자**: 검토자(독립) / 요구 분석가
- **검토자**: 보안책임자(PSO)
- **승인자**: 보안책임자(PSO)

## 3. 범위
PRO-MDCS-01-02 §5 단계2(보안요구)에 적용한다. **선행조건**: WI-MDCS-01-02-01(개발 계획) 완료. 요구 변경 시 본 지침을 재수행한다.

## 4. 입력 자료 / 산출물
- **Input**
  - 제품 요구·의도된 사용
  - 위협 모델·보안 맥락(PRO-MDCS-02-01 산출, 가용 시)
  - SW 분류표(REQUIRED 항목 식별)
  - 리스크 통제 요구(있는 경우)
- **Output**
  - [[TMP-MDCS-01-02-02-01_보안요구명세_및_검토기록_v0.1]] 작성분
  - 보안 요구명세(요구 ID·수명주기 단계·검증 방법)
  - 요구 품질 검토 기록
  - REQUIRED SW 리스크 식별 기록

## 5. 수행 절차

### 5.1 사전 준비
1. 제품 요구·의도된 사용·보안 맥락을 확보한다.
2. SW 분류표에서 REQUIRED 항목을 확인한다.
3. 요구 품질 기준(시험 가능성·무모순·추적성)을 준비한다.

### 5.2 수행 단계
1. **보안 능력 요구 도출**
   - 설치·운영·유지·폐기 각 단계에 필요한 보안 능력 요구를 도출한다(인증·접근통제·암호화·로깅·안전한 폐기 등).
2. **요구 문서화**
   - 각 요구에 고유 ID·관련 수명주기 단계·검증 방법을 부여하여 문서화한다.
3. **REQUIRED SW 리스크 식별**
   - REQUIRED SW 에 의존하는 보안 가정·리스크를 식별하고 요구로 반영한다(예: 단말 OS 최소 보안 버전).
4. **품질 검토**
   - 각 요구가 시험 가능·무모순·완전·추적 가능한지 검토하고 결함을 시정한다.
5. **검토 승인**
   - PSO 가 요구 품질·완전성을 검토·승인한다.

### 5.3 완료 조건
- [ ] 설치·운영·유지·폐기 전 단계의 보안 능력 요구 도출
- [ ] 모든 요구에 고유 ID·검증 방법 부여
- [ ] REQUIRED SW 관련 리스크·가정이 요구로 반영됨
- [ ] 요구 품질(시험 가능·무모순) 검토 수행·결함 시정
- [ ] PSO 검토·승인 기록 존재

## 6. 인터페이스 부서
- **PRO-MDCS-02-01(리스크 관리)**: 위협 모델·리스크 통제 요구 제공
- **제품기획/PM**: 제품 요구·의도된 사용 제공
- **검증팀**: 요구별 검증 방법 협의

## 7. 주의사항 / 예외 처리

### 7.1 시험 불가능 요구
- "안전해야 한다" 같은 검증 불가 요구는 시험 가능한 형태로 구체화한다(측정 기준·검증 방법 명시). 구체화 불가 요구는 채택하지 않는다.

### 7.2 요구 간 모순
- 보안 요구와 기능/유용성 요구가 충돌하면 리스크 기반으로 우선순위를 정하고 트레이드오프를 문서화한다(필요 시 PRO-MDCS-02-01 협의).

### 7.3 위협 모델 미완성
- 위협 모델이 아직 미완인 상태에서 요구를 정의해야 하면 잠정 요구로 표시하고, 위협 모델 완료 후(WI-MDCS-02-01-02) 재검토하여 확정한다.

### 7.4 REQUIRED SW 가정 위반 가능성
- REQUIRED SW 가 보안 가정을 충족하지 못할 가능성이 있으면 동반문서에 최소 요건을 명시하고 잔여 리스크로 등록한다.
