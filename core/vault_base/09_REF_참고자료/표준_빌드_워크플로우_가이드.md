# 표준 빌드 워크플로우 가이드 — 조직 repo · Worktree 기반

> 본 문서는 `/process-plan` 하네스로 새 표준을 편입할 때, **조직 repo 격리** · **기준 브랜치 격리** · **branch-per-standard** 정책을 유지하면서 Obsidian 으로 산출물을 열람·작업하는 방법을 정리한다. v2.0 부터 플랫폼 repo 와 조직 루트 repo 가 분리된 구조(org-layer)를 기준으로 한다.

상위 문서: [[표준프로세스_구성원칙]] · [[06_파이프라인_상태규약]] · [[02_문서번호체계]] · 플랫폼 `docs/architecture/org-layer.md`

---

## 1. 핵심 원칙

| 원칙 | 의미 |
|---|---|
| **조직 repo 격리** | 조직 자산(vault · inputs · sources · `.processware`)은 조직 루트 repo 하나에만 있다. git 명령은 모두 그 repo 에서(`git -C {ORG_ROOT}`) 실행되고, 플랫폼 repo 에서는 실행되지 않는다 |
| **기준 브랜치 격리** | 조직 repo 의 기준 브랜치(보통 `main`)는 `org.yaml` · 등록 메타(MOC · `*_조직추가.md`) · sync-core 결과만 누적한다. 산출물 본체는 두지 않는다 |
| **branch-per-standard** | 각 표준 산출물은 `feat/{슬러그}-output` branch 에 영구 보존 (`vault/` + `.processware/states` + `.processware/runs`) |
| **worktree 활용** | 같은 머신에서 기준 브랜치와 표준별 산출물을 동시에 열람·작업하기 위해 조직 repo 의 worktree 를 쓴다 |

플랫폼 관리 파일(`vault/00_공통관리` · `01_구성원칙` · `99_템플릿` · 폴더 `README.md`)은 어느 브랜치에서도 편집하지 않는다. 변경은 `python3 -m tools.org sync-core` 로만 들어오고 `chore(sync-core)` 커밋으로 분리한다.

---

## 2. 두 가지 워크플로우 방식

| 방식 | 명령 (조직 repo 에서) | 디스크 효율 | 추천 상황 |
|---|---|---|---|
| **A. Worktree** | `git -C {ORG_ROOT} worktree add ../acme-iso9001-view feat/iso9001-output` | .git 공유 (효율적) | 같은 머신에서 동시 작업 — **기본 권장** |
| **B. 별도 Clone** | `git clone <조직 repo url> ../acme-iso9001` | 완전 독립 (.git 중복) | 다른 머신·팀원·CI 서버 |

같은 PC 에서는 worktree, 다른 PC·CI·팀원은 clone. 어느 쪽이든 **플랫폼 repo 는 한 번만 체크아웃**하고 조직 루트만 바꿔 가리킨다.

## 3. 폴더 구조 (권장)

```
~/MyProjects/
├── processware/                ← 플랫폼 repo (에이전트 · 커맨드 · tools · core) — Claude Code 실행 위치
├── acme-org/                   ← 조직 루트 repo, 기준 브랜치 main (org.yaml · 등록 메타)
│   ├── org.yaml
│   ├── vault/ inputs/ sources/
│   └── .processware/
├── acme-iso9001-view/          ← acme-org 의 worktree: feat/iso9001-output (산출물 열람)
├── acme-iso27001-view/         ← acme-org 의 worktree: feat/iso27001-output
└── beta-org/                   ← 다른 조직 (별도 repo)
```

| 폴더 | repo / branch | 용도 |
|---|---|---|
| `processware/` | 플랫폼 repo `main` | 하네스 갱신 · `/process-plan` 실행 (작업 디렉토리) |
| `{org}-org/` | 조직 repo `main` | `org.yaml` · 표준 등록 · sync-core · `/process-plan` 의 git 대상 |
| `{org}-{표준}-view/` | 조직 repo `feat/{슬러그}-output` | 표준별 산출물 Obsidian 열람·운영 |

## 4. 새 표준 빌드 절차 (예: ACME 조직 · ISO 9001)

### Step 0. 조직 루트 준비 (최초 1회)

```bash
cd ~/MyProjects/processware
python3 -m tools.org init ../acme-org --org-id acme --name "ACME" --register
git -C ../acme-org init -b main
git -C ../acme-org add -A && git -C ../acme-org commit -m "chore(org): 조직 루트 초기화 (acme)"
git -C ../acme-org remote add origin <조직 repo url>     # 선택
```

### Step 1. 플랫폼 repo 에서 빌드 시작

```bash
cd ~/MyProjects/processware
export PROCESSWARE_ORG=acme          # 또는 PROCESSWARE_ORG_ROOT=~/MyProjects/acme-org
/process-plan ISO9001                 # 또는 /process-plan ISO9001 --org acme
```

→ `/process-plan` 이 자동 수행 (Phase −2, 모두 `git -C ~/MyProjects/acme-org`):
1. **−2-0** 조직 루트가 git repo 인지 · 다른 repo 에 중첩되지 않았는지 · 기준 브랜치(`main`) · origin 유무 · 기존 `feat/iso9001-output` 브랜치(재개) 확인
2. **−2-1** 기준 브랜치에 등록 — `org.yaml` `scopes` 에 `QMS`, `vault/00_MOC/MOC_추적성매트릭스.md` 에 MAT 번호 예약 행, (플랫폼 레지스트리에 없는 표준이면) `vault/00_공통관리/07_표준분류레지스트리_조직추가.md` → commit · push
3. **−2-2** `feat/iso9001-output` branch 생성, `_state.yaml` 에 `git.branch` · `git.base` 기록
4. Phase 0 ~ Final 실행 (preflight → analyze → design → write → trace → qa → 자가수정)
5. **−2-3/−2-4** 종료 시 4 분할 commit + push, PR 생성 안내 (`gh pr create -R <조직 repo> --base main --head feat/iso9001-output`)
6. **Phase Final** 플랫폼 repo 에 변경이 생기지 않았는지 검사

### Step 2. 빌드 완료 후 Obsidian 열람용 worktree 추가

```bash
git -C ~/MyProjects/acme-org worktree add ../acme-iso9001-view feat/iso9001-output
```

### Step 3. Obsidian 에서 vault 열기

Obsidian → **File → Open vault** → `~/MyProjects/acme-iso9001-view/vault/`

다른 표준·다른 조직의 vault 와 동시에 열어둘 수 있다.

## 5. Worktree 운영 명령

```bash
ORG=~/MyProjects/acme-org

# 현재 worktree 목록
git -C $ORG worktree list

# 새 worktree 추가 (다음 표준 빌드 후)
git -C $ORG worktree add ../acme-{표준코드}-view feat/{표준코드}-output

# 산출물 worktree 안에서 작업·commit·push
cd ~/MyProjects/acme-{표준코드}-view
# (편집 — 플랫폼 관리 파일은 제외)
git add vault/ .processware/
git commit -m "..."
git push origin feat/{표준코드}-output

# 더 이상 필요 없을 때 제거 (branch 자체는 origin 에 남음)
git -C $ORG worktree remove ../acme-{표준코드}-view
```

worktree 안에서 커맨드를 실행하려면 그 worktree 를 조직 루트로 지정한다: `PROCESSWARE_ORG_ROOT=~/MyProjects/acme-iso9001-view`.

## 6. 제약·주의사항

- **같은 branch 를 두 worktree 에서 동시 열기 불가** — git 이 자동 차단
- **조직 루트를 플랫폼 repo 안에 두지 않는다** — `/process-plan` −2-0 이 중첩을 감지하면 중단한다 (org-layer §5 결정 1)
- **기준 브랜치 디렉토리에서 산출물 직접 작업 비권장** — 산출물 변경은 worktree 또는 `/process-plan` 을 통해서
- **플랫폼 관리 파일은 편집 금지** — PreToolUse 훅 · `vault_rules validate` · qa-reviewer §13 이 차단. 조직 추가는 `*_조직추가.md`
- **`sources/` 원본은 git 제외** (조직 `.gitignore`). PDF 등을 추적하려면 LFS 와 라이선스를 먼저 확인
- **Force-push 는 worktree 의 feat branch 만** (`--force-with-lease`) — 기준 브랜치로의 force-push 절대 금지
- **재개**: 같은 슬러그 브랜치가 있으면 `/process-plan` 이 그 브랜치를 체크아웃해 `_state.yaml` 을 읽는다. 새로 시작하려면 `--restart` (일자 suffix 브랜치)

## 7. Clone 방식이 필요한 경우

같은 PC 외 환경 — 다른 노트북 · 팀원 PC · CI/CD 빌드 서버:

```bash
git clone https://github.com/Processware-AI/processware.git        # 플랫폼 (1회)
git clone <조직 repo url> acme-org                                   # 조직 루트
cd processware
python3 -m tools.org register ../acme-org
PROCESSWARE_ORG=acme /process-plan ISO9001
```

CI 에서는 조직 repo 의 `.github/workflows/vault-push.yml` 이 플랫폼을 `.platform/` 에 체크아웃해 실행하는 패턴을 따른다.

## 8. /process-plan skill 과의 정합

본 가이드의 워크플로우는 플랫폼 `.claude/commands/process-plan.md` 의 **Phase −2 (Git Branch 격리)** 와 일치한다:

- −2-0 대상 repo 검증 · 기준 브랜치 결정 ↔ Step 0 · Step 1-1
- −2-1 사전 등록 (조직 소유 파일 · 기준 브랜치 commit) ↔ Step 1-2
- −2-2 feature branch 생성 ↔ skill 자동
- −2-3 commit 정책 (4 분할 · sync-core 분리) ↔ skill 자동 · §5
- −2-4 종료 시 push · PR 안내 ↔ skill 자동
- −2-5 안전 가드 (플랫폼 repo 무변경 · 기준 브랜치 force-push 금지) ↔ 본 가이드 §6

추가로 본 가이드는 **빌드 후 worktree 추가** 단계 (Step 2~3) 를 명시한다 — Obsidian 작업 흐름.

---

## 9. 한 줄 결론

> **커맨드는 플랫폼 repo 에서, git 은 조직 repo 에서, 열람은 조직 repo 의 worktree 에서.** 다른 PC 는 두 repo 를 clone.

표준이 누적될수록 조직 repo 의 worktree 가 늘어나며, 조직마다 · 표준마다 독립 영구 보존되는 구조가 완성된다.
